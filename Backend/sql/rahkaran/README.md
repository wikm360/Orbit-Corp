# لایه‌ی معنایی راهکاران (schema `ai`)

مجموعه‌ی SQL که روی دیتابیس ریستور‌شده‌ی راهکاران (`MehvarGostar`) یک schema به نام `ai` با **84 view** می‌سازد تا Agent (یا هر کاربر SQL) به‌جای ۳۹۳ جدول خام و join های پیچیده‌ی تفصیلی، با نام‌های ساده‌ی انگلیسی و توضیح فارسی پرس‌وجو کند. شناخت دامنه و دلایل طراحی در [../../docs/rahkaran/README.md](../../docs/rahkaran/README.md) و واژه‌نامه‌ها (`GLOSSARY_*.md`) آمده است.

## اجرا

```bash
# پیش‌نیاز: pip install pymssql   (در یک venv جدا)
export RAHKARAN_SA_PASSWORD=...            # رمز SA کانتینر/سرور
export RAHKARAN_AI_PASSWORD=...            # (اختیاری) رمز کاربر فقط‌خواندنی rahkaran_ai_reader
python sql/rahkaran/apply.py               # همه‌ی فایل‌ها + توضیحات + کاربر فقط‌خواندنی
python sql/rahkaran/apply.py 30 40         # فقط فایل‌های 30 و 40
python sql/rahkaran/apply.py descr         # فقط توضیحات (MS_Description)
```

- idempotent است؛ بعد از **هر ریستور بک‌آپ جدید** دوباره اجرا شود (view ها و جدول تقویم `ai.calendar_data` با ریستور از بین می‌روند).
- اگر دیتابیس `READ_ONLY` باشد موقتاً `READ_WRITE` می‌شود و در پایان برمی‌گردد.
- محیط: `RAHKARAN_HOST` (پیش‌فرض 127.0.0.1)، `RAHKARAN_PORT` (14330)، `RAHKARAN_DB` (MehvarGostar)، `RAHKARAN_AI_USER` (rahkaran_ai_reader)، `RAHKARAN_SKIP_TF4138=1` برای نزدن trace flag.
- ترتیب فایل‌ها: `00_schema` → `10_calendar_lookup` → `15_taxonomy` → `20_reference` → `30_ledger` → `40_finance_reports` → `50_hr` → `60_payroll` → `70_assets` → `80_meta`؛ سپس `descriptions.py` (توضیح فارسی هر view و ستون) و ساخت کاربر.
- تست: `examples/run.py` (با `RAHKARAN_AI_PASSWORD`) ۶۷ سؤال نمونه ([../../docs/rahkaran/QUESTIONS.md](../../docs/rahkaran/QUESTIONS.md)) را با کاربر فقط‌خواندنی اجرا و زمان/خطا را گزارش می‌کند.

## قراردادهای نام‌گذاری
- نام‌ها `snake_case` انگلیسی؛ **همان نام ستون در همه‌ی view ها یک معنی دارد** (مثلاً `fiscal_year`, `jalali_ym`, `net_debit`, `contract_dl_code`).
- مبالغ همه به **ریال** (مگر روز/تعداد در نام ستون)؛ `debit/credit` بدون NULL؛ `net_debit = debit − credit` (مثبت بدهکار).
- تاریخ: ستون `*_date` میلادی (date) و `jalali_date` رشته‌ی شمسی `YYYY/MM/DD`؛ ماه‌های حقوق `issue_year_month` عدد شمسی `YYYYMM` (= `jalali_ym`).
- سال مالی: `fiscal_year` عدد ۴ رقمی (1404 = مهر 1404 تا شهریور 1405).
- پرچم‌ها `is_*` با مقدار 0/1.

## قواعد مهم برای تولید SQL (در hint ها بیاید)
1. برای پاسخ‌های مالی **همیشه** `is_valid_for_reports = 1` (اسناد موقت/بررسی‌شده/قطعی؛ یادداشت‌ها خارج) و برای گردش دوره `is_regular = 1` (افتتاحیه/اختتامیه/بستن حساب‌ها خارج). ستون `is_reviewed` برای داده‌ی بررسی‌شده. ماه‌های اخیر موقت‌اند: `ai.data_freshness`.
2. `ledger_lines` (693K ردیف) را همیشه با `fiscal_year` یا `voucher_date` و حساب (`sl_code`/`account_role`/`pnl_class`) محدود کنید؛ برای متن آزاد از `voucher_search` استفاده کنید.
3. قرارداد/پروژه اجرایی = `contract_dl_code` (مرکز هزینه 66xxxx)؛ دستگاه = `equipment_dl_code`؛ طرف‌حساب = `counterparty_dl_code`.
4. هزینه‌ی قراردادها: `pnl_class IN ('project_cost_wip','project_cost_recognized')` (1117 در طول سال + 5111 بعد از انتقال پایان سال).
5. برای حقوق: `payroll_monthly` (یک ردیف در هر کارمند و ماه) و برای عوامل دیگر `payroll_factor_values` با فیلتر `issue_year_month`.
6. اعداد بزرگ (ریال)؛ در پاسخ به میلیارد تومان/ریال تبدیل شود (۱ تومان = ۱۰ ریال).

## عملکرد (مهم)
- **trace flag 4138** (غیرفعال‌کردن row-goal) باید فعال باشد، وگرنه کوئری‌های `TOP n … ORDER BY` روی view های بزرگ ممکن است ۶۰ ثانیه شوند (۰.۱ ثانیه با فعال بودن). `apply.py` آن را server-wide می‌زند (با ری‌استارت SQL Server از بین می‌رود)؛ جایگزین بدون دسترسی سرور: افزودن `OPTION (USE HINT('DISABLE_OPTIMIZER_ROWGOAL'))` به انتهای هر SELECT تولیدی در لایه‌ی کانکتور.
- تقویم به جدول کوچک ایندکس‌دار `ai.calendar_data` تبدیل می‌شود تا join تاریخ سریع باشد.
- زمان‌های اندازه‌گیری‌شده (۶۷ سؤال نمونه، snapshot 2026-10-05، رم ۸GB): همه کمتر از ۴ ثانیه، بیشتر زیر ۰.۵ ثانیه؛ view های حقوق ماهانه (پیمایش ۳.۴M آیتم) ~۳ ثانیه.

## امنیت
- کاربر `rahkaran_ai_reader` فقط `SELECT` روی schema `ai` دارد؛ به جدول‌های خام (`FIN3`, `HCM3`, `SYS3.[User]` …) دسترسی مستقیم ندارد (ownership chaining از طریق مالک `dbo`). نوشتن و اجرای رویه ممنوع است.
- طبق تصمیم فعلی، view ها **همه‌ی داده‌های کسب‌وکاری شامل حقوق و اطلاعات هویتی** را در دسترس می‌گذارند (دسترسی بر اساس نقش در مرحله‌ی آخر). رمز عبور کاربران راهکاران، تنظیمات امنیتی و لاگ‌های سیستمی در هیچ view ای نیستند.
- دسترسی نقش‌ها بعداً با گروه‌بندی view ها (مالی / منابع انسانی / دارایی) و GRANT روی ستون‌ها/view های جداگانه یا ماسک ستون‌های حساس (`national_id`, `sheba`, `account_number`, `mobile`) قابل اعمال است.

## نکات و محدودیت‌های داده
- ماه‌های اخیر حسابداری موقت‌اند (آخرین سند بررسی‌شده 1405/04/31 در snapshot بررسی‌شده)؛ `ai.data_freshness`.
- سود محاسبه‌شده «برآورد» از دفتر کل است (`income_summary_year.profit_estimate`)؛ استهلاک ماشین‌آلات 5112 در پایان سال به قراردادها تسهیم می‌شود.
- `ai.asset_ledger_reconciliation` اختلاف حدود ۳٪ بین ماژول دارایی و دفتر کل نشان می‌دهد (معمول: دارایی‌های نگهداری‌شده برای فروش، فروش‌رفته‌ها و اسناد دستی).
- جنسیت `1 = مرد` (enum `PersonGender`)؛ همه‌ی کارکنان فعال مرد و قراردادی‌اند.
- `ai.attendance_monthly` عملاً خالی از اطلاعات حضور است (از 1403 فقط شاخص پاداش پیشنهادات).

## فهرست view ها

### پایه و مرجع

| view | توضیح |
|---|---|
| `ai.calendar` | تقویم روزانه ۲۰۰۰ تا ۲۰۴۰ با تاریخ شمسی و تقویم مالی (سال مالی از اول مهر). برای تبدیل تاریخ میلادی↔شمسی با JOIN روی gregorian_date. |
| `ai.lookup_values` | فرهنگ مقادیر enum سیستم (SYS3.Lookup) با ترجمه‌ی فارسی و انگلیسی؛ برای رمزگشایی کدهای عددی در جدول‌های خام. |
| `ai.fiscal_years` | سال‌های مالی با برچسب واقعی ۴ رقمی (fiscal_year)، بازه‌ی تاریخ (مهر تا شهریور)، وضعیت بسته‌شدن و تعداد اسناد. |
| `ai.accounts` | نمودار حساب‌ها: گروه > کل > معین با ماهیت، طبقه‌ی مالی، طبقه سود و زیان (pnl_class)، نقش تجاری (account_role) و کلید ماهیت هزینه. |
| `ai.dl_accounts` | حساب‌های تفصیلی (اشخاص، شرکت‌ها، مراکز هزینه، پروژه‌ها، حساب بانکی، تسهیلات، سایر) با دسته‌بندی کسب‌وکاری و شناسه مرجع. |
| `ai.parties` | اشخاص حقیقی و حقوقی (کارکنان، تأمین‌کنندگان، کارفرماها) با کد ملی، تماس و آدرس اصلی و پیوند به کارمند/تفصیلی. حاوی اطلاعات هویتی. |
| `ai.cost_centers` | مراکز هزینه: قراردادها/پروژه‌های اجرایی (is_contract، کد 66xxxx)، ماشین‌آلات سنگین (41)، کامیون (42)، خودرو سبک (43)، تجهیزات ثابت (44). |
| `ai.projects` | پروژه‌های شرکتی (GNR3.Project). بُعد پروژه در هزینه‌ها بیشتر «عمومی(اداری)» است؛ قرارداد واقعی همان مرکز هزینه 66xxxx است. |
| `ai.bank_accounts` | حساب‌های بانکی شرکت با بانک، شعبه، نوع حساب، شبا و کد تفصیلی. |
| `ai.users` | کاربران راهکاران (بدون اطلاعات ورود). |

|---|---|

| `ai.voucher_search` | جستجوی متنی سبک در توضیحات سند و ردیف سند (بدون join ابعاد) برای پیدا کردن اسناد؛ سپس با voucher_id به ledger_lines/vouchers وصل کنید. |

| `ai.trial_balance_gl_year` | تراز آزمایشی در سطح کل (GL) برای هر سال مالی. |
| `ai.balance_sheet_year` | ترازنامه: مانده‌ی پایان سال حساب‌های ترازنامه‌ای در سطح کل (قبل از اسناد بستن). |
| `ai.balance_sheet_check_year` | کنترل ترازنامه: جمع حساب‌های ترازنامه‌ای + سود و زیان بسته‌نشده + انتظامی باید صفر شود؛ شامل جمع دارایی/بدهی/حقوق صاحبان سهام. در سال جاری هزینه‌ی قراردادها در GL 1117 (ترازنامه) است. |

| `ai.income_summary_year` | خلاصه سود و زیان هر سال مالی: درآمد، هزینه‌ی قراردادها، هزینه‌ی ماشین‌آلات، اداری، مالی و برآورد سود. |
| `ai.revenue_lines` | ردیف‌های درآمد دفتر کل (اسناد عادی معتبر) با قرارداد و طرف‌حساب. |
| `ai.cost_lines` | ردیف‌های هزینه دفتر کل (قراردادها، ماشین‌آلات، اداری، مالی …) با قرارداد، دستگاه و ماهیت هزینه. |
| `ai.cost_by_nature_year` | هزینه به تفکیک ماهیت (حقوق، اجاره، سوخت، پیمانکار، مواد …) و سال مالی با ادغام معین‌های 1117xx/5111xx/5112xx/6213xx. |
