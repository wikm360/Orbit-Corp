# بازبینی کد، چک‌آپ امنیتی و پلن اجرا (قبل از انتشار روی سرور عمومی)

وضعیت: **فقط گزارش و پلن**؛ هیچ کدی هنوز تغییر نکرده است (به‌جز ساخت فایل `.env.production`). بعد از بازبینی شما، موارد تأییدشده اجرا می‌شود.
تست‌ها: `pytest` کامل = ۱۲۲ تست سبز (با Postgres محلی). ورود کاربر فقط‌خواندنی با اطلاعات `.env` به SQL Server محلی موفق است و جدول خام برایش بسته است. اعتبارسنج SQL در آزمایش دستی جلوی `FIN3.*`، `sys.*`، `master..`، چند دستور، `EXEC/INTO/OPENROWSET` را گرفت.

- `Assets/` (۳۷GB) و `data/` نباید به سرور/گیت بروند (`git add` با مسیر مشخص).

## پ) فایل `.env.production` (ساخته شد؛ بدون commit)
`Backend/.env.production` (دسترسی 600، در `.gitignore` با الگوی `.env*`): کپی `.env` با تغییرات
`ENVIRONMENT=production`، `DEBUG=false`، `REQUEST_LOGGING_ENABLED=false`، `RAHKARAN_DB_HOST=mssql`، **رمز جدید SA و رمز جدید کاربر خواننده**، `RAHKARAN_DB_QUERY_TIMEOUT_SECONDS=30`.
روی سرور آن را به نام `.env` بگذارید. رمز کاربر خواننده را هنگام اجرای `apply.py` (`RAHKARAN_AI_PASSWORD`) و رمز SA را هنگام بالا آمدن اولیه‌ی mssql (volume تازه) با همین مقادیر بدهید. هنوز باید: `CORS_ORIGINS` را به دامنه‌ی https تغییر دهید.

## ت) پلن اجرا (بعد از تأیید شما)

**مرحله ۱ — حداقل لازم برای انتشار (P0)**
1. بستن ثبت‌نام عمومی: تنظیم `ALLOW_PUBLIC_REGISTRATION=false` (پیش‌فرض false)، ساخت کاربر توسط ادمین؛ تست.
2. allow-list ابزار: تنظیم `RAHKARAN_ALLOWED_EMAILS`/`RAHKARAN_ALLOWED_ROLES`؛ ابزار فقط برای مجازها در registry/اجرا؛ غیرفعال در گروه چت؛ تست.
3. اصلاح A1/A2 (مالکیت بازخورد، احراز هویت freshness) + تست.
4. docker-compose امن: حذف همه‌ی `ports` به‌جز proxy؛ `backend`، `postgres`، `redis`، `mssql` فقط در شبکه‌ی داخلی؛ Redis با رمز؛ رمز SA بدون پیش‌فرض (`:?`)؛ حذف `external: true`؛ `override.yml` فقط dev.
5. reverse proxy (Caddy) با TLS خودکار، HSTS، rate limit، بستن `/docs` و `/openapi.json`؛ فایروال (ufw 22/80/443).
6. اجرای سرویس‌ها غیر root + `no-new-privileges` + محدودیت منابع + rotate لاگ داکر.
7. غیرفعال‌سازی لاگ بدنه‌ی پاسخ برای مسیرهای حساس حتی اگر لاگ روشن شد.

**مرحله ۲ — حفاظت داده (P1)**
8. ماسک PII در خروجی ابزار + حذف ستون‌های حساس از ورودی مدل (قابل پیکربندی)؛ A3/A4/A5/A6/A7/A8/A10 اصلاحات کد.
9. rate limit و سهمیه‌ی کاربر برای ابزار؛ سقف هم‌زمانی و زمان کل.
10. رمزگذاری دیسک/حجم‌ها، رویه‌ی حذف `.bak`، بک‌آپ رمزگذاری‌شده‌ی Postgres و SQL Server.
11. تصمیم لایسنس SQL Server (Express/Standard) و اجرای آن.
12. تصمیم درباره‌ی provider مدل (مستقیم/خودمیزبان) و قرارداد/تأیید شرکت.

**مرحله ۳ — سخت‌سازی و عملیات (P2)**
13. قفل حساب/۲FA ادمین‌ها، محدودیت IP برای مسیرهای `/admin` و `/accounting-db/*`.
14. هشدار و مانیتورینگ؛ گزارش هفتگی پرسش‌های پرتکرار/ناموفق از `db_query_logs`.
15. اسکریپت restore/refresh خودکار بک‌آپ جدید روی سرور (restore + `apply.py` + تست دود + سوییچ).
16. تست نفوذ سبک: prompt injection از داده، تلاش دور زدن اعتبارسنج، brute-force، اسکن پورت.

## ث) تصمیم‌هایی که از شما لازم است
1. ثبت‌نام: کاملاً بسته (فقط ادمین) یا دعوت‌نامه؟ چه کسانی (نقش/ایمیل) اجازه‌ی ابزار مالی دارند؟ در چت گروهی غیرفعال شود؟
2. پیکربندی ماسک PII: همه‌ی کد ملی/شبا/حساب/موبایل ماسک شود؟ نام کارکنان در خروجی حقوق نمایش داده شود؟
3. provider مدل: ادامه با `gapgpt` یا مستقیم/خودمیزبان؟ (تأیید شرکت لازم است.)
4. نسخه‌ی SQL Server: Express (رایگان) یا Standard؟
5. دامنه و TLS: دامنه‌ی سرور چیست؟ Caddy با Let's Encrypt مناسب است؟
6. مخزن گیت‌هاب private است؟ مستندات حاوی نام و ارقام واقعی در آن بمانند؟
