# برنامهٔ فرانت Orbit

مرجع قرارداد: «مستندات هماهنگی فرانت.html» ارائه‌شده توسط تیم بک‌اند، ۲۵ سپتامبر ۲۰۲۶.

## ۱. هماهنگی با قرارداد چت

- نگهداری وضعیت ساختاریافتهٔ `{ status, tool?, args? }` در SSE و WebSocket.
- نگاشت هر ۹ ابزار به توضیح فارسی؛ جایگزینی وضعیت در هر مرحله، پایان نشانگر با شروع متن و پاک‌سازی در پایان/خطا/تغییر گفتگو.
- پشتیبانی از متن فارسی وضعیت در بک‌اند قبلی و ابزارهای ناشناخته، بدون نمایش آرگومان‌های خام.
- تفکیک پاسخ‌های هم‌زمان گروهی با `reply_to_message_id` و جلوگیری از ورود پاسخ دیرهنگام به گفتگوی دیگر.
- ویرایش عنوان شخصی و گروهی با PATCH؛ حفظ `linked_project_id` فعلی شخصی و ارسال null برای گروهی.
- عنوان اختیاری هنگام ساخت گروه؛ نمایش عنوان واقعی پاسخ سرور، مستقل از نام پروژه.

## ۲. تجربه و طراحی

- پوستهٔ فارسی راست‌به‌چپ با قلم محلی وزیرمتن، نوار کناری سرمه‌ای و تأکید فیروزه‌ای.
- تاریخچهٔ قابل جست‌وجو با تمایز گفتگوهای شخصی و گروهی.
- صفحهٔ شروع با پیشنهادهای قابل ویرایش، انتخاب محدودهٔ دانش و فرم جداگانهٔ ساخت گروه.
- سربرگ عنوان، ویرایش عنوان، وضعیت اتصال گروه، پیام‌های خوانا و نشانگر فعالیت ابزار.
- ورودی پیام با پیوست، منشن، توقف پاسخ شخصی و حالت‌های بارگذاری/خطا.
- یکپارچگی بصری اسناد و فضای کاری، نمایش موبایل، فوکوس صفحه‌کلید و کاهش حرکت.

## ۳. اعتبارسنجی

- تست قرارداد برای وضعیت ابزارها، چند رویداد متوالی، بسته‌های شکستهٔ SSE، عنوان و حفظ اتصال پروژه.
- TypeScript، ESLint و ساخت production.
- بررسی مرورگری دسکتاپ و موبایل با API آزمایشی مستقل، شامل خطا، ویرایش عنوان و گفتگوهای گروهی.

## وابستگی به بک‌اند

نسخهٔ موجود در مخزن هنگام شروع کار، `title` را در `ConversationUpdate` ندارد و بخش‌هایی از قرارداد قدیمی را اجرا می‌کند. برای کارکرد ویرایش عنوان در محیط واقعی، نسخهٔ شرح‌داده‌شده در سند باید روی سرور منتشر شود. قابلیت‌های حافظه و خواندن سند از همان چت مصرف می‌شوند؛ API جدیدی برای آن‌ها ساخته نمی‌شود.

## نتیجهٔ اجرا — ۲۵ سپتامبر ۲۰۲۶

موارد بالا پیاده‌سازی شد. منطق SSE و WebSocket از قرارداد سند استفاده می‌کند و مراحل ابزارها در هر پاسخ جایگزین می‌شوند. وضعیت پاسخ‌های گروهی مستقل است. تغییر مسیر، توقف پاسخ شخصی، لینک مستقیم گفتگو و پیوست فایل در گفتگوی تازه بررسی شدند.

اعتبارسنجی انجام‌شده:

- ۸ تست قرارداد در `tests/chat-contract.test.cjs`: موفق.
- تست مرورگری `tests/chat-browser.cjs` در Chrome با HTTP و WebSocket ساختگی: موفق؛ شامل جست‌وجو، عنوان شخصی و گروهی، عنوان پیش‌فرض سرور، منابع، چند پاسخ هم‌زمان، تغییر مسیر، توقف و آپلود.
- اندازهٔ دسکتاپ ۱۴۴۰×۱۰۰۰ و موبایل ۳۹۰×۸۴۴: بررسی تصویری؛ بدون اسکرول افقی و خطای JavaScript.
- TypeScript، ESLint، `next build --webpack` و `git diff --check`: موفق.

این تست‌ها اتصال به سرور واقعی یا اجرای مدل و ابزارهای بک‌اند را تأیید نمی‌کنند. بررسی نهایی محیط واقعی باید پس از انتشار بک‌اند مطابق سند انجام شود.

### اجرا و تکرار بررسی‌ها

از پوشهٔ `Frontend`:

```sh
npm ci
npm run dev
npm test
npm run lint
npm run build
```

آدرس API از `NEXT_PUBLIC_API_URL` خوانده می‌شود. برای تست مرورگری، فرانت باید روی `http://127.0.0.1:3000` اجرا باشد و Playwright به‌صورت جداگانه در محیط تست نصب باشد. `PLAYWRIGHT_MODULE` مسیر نصب Playwright، `BROWSER_CHANNEL=chrome` استفاده از Chrome موجود، `APP_URL` آدرس جایگزین فرانت، و `ARTIFACT_DIR` مسیر خروجی تصاویر را تعیین می‌کند:

```sh
BROWSER_CHANNEL=chrome npm run test:browser
```

تست مرورگری پروفایل مستقل می‌سازد و درخواست‌های API/سوکت را جایگزین می‌کند؛ دادهٔ آزمایشی وارد برنامه یا بک‌اند واقعی نمی‌شود. وابستگی runtime جدیدی برای رابط اضافه نشده است.

## ماژول «گزارش حجم عملیات» (`/volume-reports`)

کد در `src/features/volume-reports/` و صفحه‌ها در `src/app/(main)/volume-reports/` است. قرارداد API از `Backend/.agents/flows/volume-report.md` و `reference/api-endpoints.md` گرفته شده؛ نوع‌ها در `types.ts` و کلاینت در `api/volumeReportApi.ts`.

### فعال‌بودن ماژول
بک‌اند router را فقط با `VOLUME_REPORT_ENABLED=true` ثبت می‌کند و **پرچم صریحی در `/auth/me` نیست**. فرانت با یک probe روی `GET /volume-reports/catalog` تشخیص می‌دهد (۲۰۰ = روشن، ۴۰۴ = خاموش). نتیجه به‌ازای توکن کش می‌شود (`useVolumeEnabled`)؛ وقتی خاموش است آیتم منو و ورودی فایل‌منیجر نمایش داده نمی‌شود و `/volume-reports` به `/chat` برمی‌گردد.

### صفحه‌ها
| مسیر | محتوا |
|---|---|
| `/volume-reports?tab=reports\|review\|settings&project=` | فهرست گزارش‌ها (فیلتر وضعیت)، صف بازبینی، تنظیمات |
| `/volume-reports/new` | ویزارد ۴ مرحله‌ای (مشخصات ← فایل‌ها ← بازبینی و شروع ← پیشرفت). `?project=&docs=a,b` از فایل‌منیجر؛ `?report=` ادامه‌ی پیش‌نویس |
| `/volume-reports/[id]` | جزئیات: نتایج (هلدینگ/شرکت/کارگاه، کارت آیتم‌ها، نمودار ECharts، drill-down، سایر/مشکل‌دار/بدون حجم)، بازبینی، منابع و هشدارها؛ خروجی، انتشار، نسخه‌ی جدید |

### قواعد پیاده‌سازی
- **اعداد:** کمیت‌ها رشته‌ی دسیمال‌اند و فقط با عملیات رشته‌ای فرمت می‌شوند (`lib/format.ts`، گرد کردن half-up دقیق)؛ `parseFloat` فقط برای رسم نمودار (`toChartNumber`) و هرگز برای عدد نمایش‌داده‌شده.
- **تاریخ:** API میلادی (`YYYY-MM-DD`)، UI شمسی (`lib/jalali.ts` بدون وابستگی؛ تست با Intl روی ۱۲ سال روز-به-روز). کاربر تاریخ شمسی تایپ می‌کند (`۱۴۰۵/۰۶/۰۱`).
- **polling:** `lib/polling.ts` + `hooks/useRunProgress.ts` — ۲ ثانیه (با افزایش تدریجی تا ۸) در تب فعال، ۱۵ ثانیه در تب پنهان، با بازگشت به تب فوراً بیدار می‌شود، با خروج از `processing` یا ۵ خطای پیاپی متوقف می‌شود. WebSocket نیست.
- **گزارش فعالیت:** `hooks/useReportActivity.ts` (کل تاریخچه را از `GET /{id}/activity` می‌خواند و در حال `processing` با cursor `after_id` هر ۲ ثانیه ادامه می‌دهد) و `components/ActivityPanel.tsx` (لاگ زمانی، جدیدترین پایین، اسکرول خودکار، «در انتظار پاسخ مدل — گام x از y»، هشدار بی‌فعالیتی). حین پردازش و در حالت failed زیر ProgressCard، و بعد از پایان در تب «گزارش فعالیت».
- **پروژه‌ها:** از `loadWorkspace` (مسیر تیم‌ها)، پس admin غیرعضو هم همه‌ی پروژه‌ها را می‌بیند. ویرایش تنظیمات = admin یا leader هر تیمی (هم‌قاعده با بک‌اند)؛ بقیه فقط‌خواندنی و تب «حافظه‌ی تصمیم‌ها» برایشان مخفی است.
- **خطای قفل انتشار:** پیام ۴۰۹ بک‌اند (`Publish blocked: [...]`) پارس و با علت و راهنما در دیالوگ نشان داده می‌شود (`parseGateError`).
- **چت:** artifact `volume_table` با `VolumeTableCard` رندر می‌شود (ستون واحد از `unit_by_row`، یادداشت‌ها، لینک گزارش).
- eslint این مخزن `react-hooks/set-state-in-effect` را اجباری می‌کند؛ بارگذاری در effect با `runSoon` (`lib/defer.ts`) شروع می‌شود (همان الگوی `useProjectMemories`).

### تست‌ها
`tests/volume-reports-contract.test.cjs` (۱۸ تست، در `npm test`): تبدیل شمسی، فرمت اعداد، سیاست و حلقه‌ی polling، منطق کارت سؤال (ترتیب، اعتبارسنجی، payload)، تأیید گروهی، ویزارد، گزینه‌های نمودار، و رندر `QuestionCard` / `VolumeTableCard` / `SourceDetails`. تست مرورگری (Playwright) برای این ماژول نوشته نشده.

### ناهمخوانی‌ها/کمبودهای بک‌اند که هنگام ساخت فرانت دیده شد
1. پرچم فعال‌بودن ماژول در `/auth/me` یا `/health` نیست (probe استفاده شد).
2. `review/groups` فیلد `confidence` نداشت → در بک‌اند اضافه شد؛ `/catalog` هم `rollup_of` نداشت (برای drill-down جمع آسفالت) → اضافه شد.
3. `trace`/`lines` فقط با `site_id` فیلتر می‌شوند؛ drill-down سطح شرکت چند درخواست (یکی برای هر کارگاه) می‌زند.
4. خطای قفل انتشار در متن `detail` (رشته‌ی JSON) می‌آید نه ساختار؛ فرانت پارسش می‌کند.
5. ثبت‌نام شرکت جدید فقط admin/leader؛ کاربر عادی در ویزارد نمی‌تواند شرکت بسازد (پیام راهنما نشان داده می‌شود).
6. `sheet_log` پیش از اولین اجرا خالی است؛ بنابراین مرحله‌ی «فهرست شیت‌ها و هشدارها» بعد از اجرا (مرحله‌ی ۴) نشان داده می‌شود، نه پیش از آن.
